Evidence
--------
- Scanout-slot reuse is exonerated. Frames 3, 5 and 7 reuse slot fb=56 and
  frames 4 and 6 reuse fb=57; every one reached "glFinish done" and the run
  continued to frame 8. The three-buffer pool is not the trigger.
- The failure follows client source-buffer reuse. With SDL's shorter source
  cycle the hang was on frame 3; with six D1 source buffers it moved to frame 8.
- Exact hang location: after "draw begin" and before "glFinish done" of frame 8,
  i.e. inside the rotated draw sampling a reused client buffer (the source
  EGLImage had already been reported "image ok").
- D3 (fault capture): CONFIG_PSTORE / PSTORE_CONSOLE / PSTORE_COMPRESS are set,
  but there is no persistent backend (/sys/fs/pstore is empty, no ramoops in the
  kernel command line). /sys/class/devcoredump is globally disabled
  ("disabled"), and a hard SoC hang would not leave a readable dump. No kernel
  change is proposed.
- Every hang required a hard power reset; the durable userspace trace is the
  only evidence.

Remaining uncertainty
---------------------
The evidence is consistent with two causes that this work did not separate:
  1. missing/insufficient producer-to-consumer synchronization on a reused
     client DMA-BUF (the implicit dma-buf fences not ordering the client's new
     writes before the compositor's GPU read), or
  2. an EGLImage/import-reuse behavior in this Mesa/msm combination (the cached
     imported image is reused after the client rewrites the buffer), including
     a possible freedreno/msm fault.
glFinish() proves the compositor's own GL work completed; it does not prove the
client's writes were complete, so it cannot distinguish these.

Future investigation (NOT implemented, needs approval)
------------------------------------------------------
- Explicit producer fence handling before sampling a reused client buffer
  (for example EGL_ANDROID_native_fence_sync, or exporting the dma-buf's sync
  file and waiting) is the natural next mechanism. It is deliberately not
  implemented in 3C.
- A fresh EGLImage per commit would test the stale-image hypothesis; also not
  attempted.
- No client-side flush, sleep or delay workaround was added.
